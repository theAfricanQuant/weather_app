Your guided study plan

This course is for a Python developer learning Rust by reading one real app. Take one lesson at a time; you do not need to understand the whole codebase before you begin. In each lesson, make a prediction, watch the short video section, trace the related source, try the exercise, and only then open the answer.

  1. Predict first. Say what you think the code will do. A wrong first guess is useful because it shows us which idea to unpack.
  2. Watch the assigned clip. Use the time range in the lesson. Pause or replay; the clip is a guide, not a race.
  3. Read the Rust slowly. Follow one value through the functions. Notice its type, who owns it, and whether a function borrows or consumes it.
  4. Try the task before the answer. If you get stuck, use the hints or ask for a smaller clue.
  5. Explain the why. Connect the design to Python and say what Rust's compiler is checking for.

For each new idea, the explanation will cover what the code does, why this Rust design is useful, what a Pythonista might expect instead, and what subtle type or ownership rule to notice. We will use Nigerian examples where they make the idea clearer: a market ledger, a danfo route, or a dispatch rider carrying a message. The metaphors help us remember the rule; the Rust type and code remain the precise version.

Python and Rust are not one-to-one. For example, a Rust Option<T> makes a missing value explicit in the type, while Python commonly uses None at runtime. Rust's Result<T, E> makes a success-or-error path explicit, while Python code often raises or catches exceptions. When ownership and borrowing appear, we will compare Rust's compile-time rules with Python's runtime-managed object lifetimes rather than pretending the two behave identically.

Instructions for guided sessions

When using this course with a tutor, ask them to stay on the current lesson and explain each new Rust choice in detail: what it means, why this project uses it, what the closest Python pattern is, and where the comparison stops matching. Ask them to pause on compiler messages and unpack terms such as type inference, Option, Result, ownership, move, borrow, and &mut when they appear. Work one small step at a time; do not jump straight to a finished solution. Before changing or deleting code in Zed, get the exact Vim-mode cursor motion and edit keys. Keep the explanation readable within the page margins and use Nigerian metaphors when they clarify the idea.

Start here: create our Rust crate in this folder

  1. Open the regular Tuxedo OS Terminal.
  2. These instructions are for me, Ricky, on my Tuxedo OS setup. If you are checking out this repository on another computer, operating system, or in a different folder, replace my example absolute path with the absolute path to your own course folder. On my machine, I move into the folder and check the location:
    cd "/home/siseng/Documents/08_Personal/programing_languages/Rust/weather_app" && pwd
    The pwd output should match the folder in your cd command. On my machine it ends with /Rust/weather_app; your path will depend on where you saved the checkout. This check matters: Cargo creates files in the terminal's current folder, like a dispatch rider delivering a parcel to the address written on the waybill.
  3. If there is not already a Cargo.toml in this folder, create the executable crate here:
    cargo init --bin --vcs none
  4. Open the whole project folder in Zed from that same terminal:
    zed .
    If the terminal says zed: command not found, open Zed from the Tuxedo OS app launcher and choose File → Open Folder, then select the same course folder. In Zed's file tree, open src/main.rs. We open the folder so the editor can show the Rust source, Cargo.toml, and our lesson notes together.
  5. Back in the terminal, start the new crate from this folder:
    cargo run

Use cargo init because this folder already contains our lessons; cargo new would create a second nested folder. The --bin flag asks Cargo for an executable crate, and --vcs none keeps Cargo from trying to initialize Git before we deliberately set up the project repository. Cargo creates Cargo.toml and src/main.rs. Then cargo run compiles and launches the starter program. If the folder already has a Cargo.toml, do not initialize it again; tell me what you see and we will inspect it together.

We will grow this crate in the current folder as we learn. The video and reference app are our map, not a clone we edit. Keep the first run simple: the app's main.rs is the gate at a busy market; it starts the program, and later we will add the stalls that do the actual work.

Keep progress and publish the lessons

We will make a small Git commit at each learning milestone, then push those snapshots to a new public GitHub repository. A commit is like a dated page in our market ledger; a push carries that page to GitHub so we can share and continue the work from another machine.

  1. Start and run the local crate.
  2. Check Git's current root with git rev-parse --show-toplevel. We will make sure Git sees this weather project before staging any files.
  3. Initialize this folder as its own repository, inspect the staged files, and commit the first checkpoint.
  4. Create an empty public GitHub repository, connect it as origin, then push the checkpoint to main.
  5. The workflow at .github/workflows/pages.yml assembles only the lesson files and publishes them after a push to main.
  6. Put the published lesson URL in the root README.md, so readers can open the course in a browser without cloning the code.

Before the first Pages deployment, choose Settings → Pages → Build and deployment → Source → GitHub Actions. On GitHub Free, Pages is available for public repositories; the published Pages site itself is public, so never put secrets in the course or crate. The README has a placeholder for the live link until the repository name and owner are settled.

We will take the Git steps together. First we will check which repository Git sees, then stage only this project, inspect the staged files, commit, connect the remote, and push. No command should scoop up the parent Rustlings workspace by accident. GitHub Actions can publish the Pages artifact, but it does not create the repository or upload our local commits; Git push does that.

Git steps we will do together after the crate runs

First we check the current root. We do not stage anything until the output identifies this weather project as its own repository:

git rev-parse --show-toplevel
git status --short

Then we initialize Git, inspect the files before committing, and save the first checkpoint:

git init -b main
git add -A
git status --short
git commit -m "Start Rust weather learning project"

On GitHub, create an empty public repository under the account you want to use. Leave “Add a README” unchecked because our local README already exists. Authenticate the terminal with gh auth login, verify it with gh auth status, then replace the placeholders in these commands with the actual owner and repository:

git remote add origin https://github.com/theAfricanQuant/weather_app.git
git push -u origin main

We will run each command only after checking the previous output. If git init reports a permission error or git rev-parse still points at the parent Rustlings folder after initialization, stop there and ask for help before staging.

Zed with Vim bindings

Use these common Vim-mode keys while editing. Press Esc to return to normal mode; press i to insert text. In normal mode, h, j, k, and l move left, down, up, and right; w and b move by words.

For a line edit, first navigate to the line and check that it is the right one. dd deletes the current line, u undoes the last edit, and :w saves. Before any deletion exercise, the lesson will tell you what to find and which keys to press. Zed's Vim mode is configurable and is not identical to every Vim setup; see the Zed Vim mode guide.
