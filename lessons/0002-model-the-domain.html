Before the explanation

LocationQuery has a city/state variant and a latitude/longitude variant. Which input shape can it not represent?

One ticket, one route

The app uses a Rust enum whose variants carry different data. This encodes a rule in the type: a query is either a city/state pair or a coordinate pair. In models.rs, a separate struct then bundles that location with a start and end date.

enum LocationQuery {
    CityState { city: String, state: String },
    Coordinates { latitude: f64, longitude: f64 },
}

struct WeatherQueryRequest {
    location: LocationQuery,
    start_date: chrono::NaiveDate,
    end_date: chrono::NaiveDate,
}

Think of LocationQuery like a danfo ticket with one destination format: it carries either a named route or GPS coordinates. The type prevents the “both at once” arrangement before the API call starts.

Weather fields that may be missing use Option<T>. For example, a current temperature can be Some(value) or None; “missing” is represented explicitly rather than by a magic number.

Pythonista lens — make invalid shapes harder to express: Python might pass a dictionary with keys such as city, latitude, and longitude, then check at runtime which combination is present. Here, LocationQuery is an enum: it must be one named variant, and each variant carries only the fields that belong to it. The compiler can reject code that tries to construct an impossible mixture. A Rust Option<f64> resembles a number-or-None in Python, but Rust makes callers handle both Some(number) and None explicitly.
Pythonista comparison: two location shapes

Python 3.10+ can describe the alternatives with a union of dataclasses. These annotations help tools and readers, but Python does not enforce them at runtime the way Rust checks enum construction at compile time.

from dataclasses import dataclass


@dataclass(frozen=True)
class CityState:
    city: str
    state: str


@dataclass(frozen=True)
class Coordinates:
    latitude: float
    longitude: float


LocationQuery = CityState | Coordinates

Code along: give a weather request a Rust shape

We will create one module file, then use its types from main.rs. In Zed's file tree, right-click the src folder and choose New File. Name it models.rs. Replace its contents with:

#[derive(Debug)]
pub enum LocationQuery {
    CityState { city: String, state: String },
    Coordinates { latitude: f64, longitude: f64 },
}

#[derive(Debug)]
pub struct WeatherQueryRequest {
    pub location: LocationQuery,
    pub start_date: String,
    pub end_date: String,
}

Now replace all of src/main.rs. In Zed Vim mode, use Esc, gg, dG, then i; paste this block with Edit → Paste, then save with Esc, :w, Enter.

mod models;

use models::{LocationQuery, WeatherQueryRequest};

fn main() {
    let request = WeatherQueryRequest {
        location: LocationQuery::CityState {
            city: String::from("Lagos"),
            state: String::from("Lagos"),
        },
        start_date: String::from("2026-10-21"),
        end_date: String::from("2026-10-22"),
    };

    println!("{request:#?}");
}

Save both files, then run cargo run in the project folder. The terminal should print the request and its nested CityState value. mod models; connects src/models.rs to the crate; use brings its names into this file. The pub keywords allow the parent module to use items declared inside models. The dates are strings for now; Lesson 4 will validate user text before we treat it as a request.

Pythonista lens: models.rs is roughly like a Python module, but Rust does not include every file just because it exists. We declare the module with mod models;. The enum is like a carefully shaped set of alternatives: a location is either a city/state pair or coordinates. String::from creates owned Rust strings; Python manages string lifetimes for you, while Rust will make ownership rules explicit as we use values.
