If the API omits a daily measurement, what does this app place in the matching record slot?

Normalize at the boundary

weather_service.rs defines private structs that describe only the JSON fields this app needs. Serde's Deserialize derive maps JSON into those structs. The service then checks for the daily block and builds a clean Vec<WeatherDayRecord> for the rest of the program.

#[derive(Debug, Deserialize)]
struct OpenMeteoDaily {
    time: Vec<String>,
    temperature_2m_max: Option<Vec<f64>>,
    temperature_2m_min: Option<Vec<f64>>,
    precipitation_sum: Option<Vec<f64>>,
    weather_code: Option<Vec<i32>>,
}

The time list establishes how many day records exist. Optional measurement arrays are expanded to that length. If an array is absent or has a mismatched length, its slots become None. Each record then carries a date, optional measurements, a readable description, and a source label.

Like a produce stall sorting a mixed delivery into labeled baskets, the service turns outside data into the app's own steady shape before the GUI handles it.

Pythonista lens — parse into known fields, then handle absence: In Python it is common to keep decoded JSON as nested dictionaries and discover a missing key when indexing it. Serde deserializes the response into Rust structs with named fields and declared types. Optional API fields become Option<T>, so a missing measurement is not silently confused with zero. The service normalizes uneven arrays before the rest of the app sees them; the GUI can then rely on one predictable record shape. This boundary is like checking a delivery at the market gate before sending it to each stall.
Pythonista comparison: read optional fields from JSON

Python's dict.get() is a familiar way to handle a missing key. In Rust, deserializing into typed structs and using Option<T> makes those missing values explicit after parsing.

payload = response.json()
daily = payload.get("daily", {})
dates = daily.get("time", [])
precipitation = daily.get("precipitation_sum")
