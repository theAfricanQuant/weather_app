Before the explanation

For a city/state query, what happens before the weather forecast request?

The route depends on the location type

weather_service::fetch_weather matches the request's location. A city/state input calls geocoding_service to get latitude, longitude, and a timezone hint. A coordinate input validates the numeric ranges and already has its coordinates.

City and stateGeocode to coordinates
CoordinatesValidate latitude/longitude
Date rangeChoose archive or forecast
HTTP responseCheck status, then parse JSON

The geocoder is like a motor-park dispatcher who turns a place name into a destination pin. One important boundary: this repository's geocoder sends countryCode=US and searches for a US state. That city/state route is US-only in the current code. Coordinate mode is available for other regions.

Then fetch_weather_range chooses the forecast endpoint for today/future dates and the archive endpoint for dates in the past. A range crossing today is split into two calls and merged by date.

Pythonista lens — turn choices into typed routes: A Python implementation might pass a string like "city" or a dictionary and branch on it later. Here, matching on LocationQuery makes the two routes explicit: city/state first needs geocoding, while coordinates already identify a point. The function signatures also show what comes back and what can fail. This is useful when an HTTP request has several stages: resolve a place, choose the correct forecast or archive endpoint, then convert the response. The enum acts like a danfo ticket for one valid route at a time.
