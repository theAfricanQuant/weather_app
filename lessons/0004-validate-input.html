Before the explanation

parse_date_range returns a Result. What should it return when both dates parse and the start is not after the end?

Validation is a gate with a receipt

The UI starts with strings because that is what text boxes hold. Before networking, build_request checks the date range, matches on the input mode, trims fields, parses coordinate strings into f64, and builds the typed request. The functions return Result so an invalid input has a clear path back to a status message.

fn parse_date_range(&self) -> Result<(NaiveDate, NaiveDate), String> {
    let start = date_utils::parse_date(&self.start_date_input)?;
    let end = date_utils::parse_date(&self.end_date_input)?;
    if start > end {
        return Err("Start date must be on or before End date.".to_owned());
    }
    Ok((start, end))
}

This omits the empty-field checks to keep the pattern visible. The ? operator returns early if parsing fails. The final Ok is reached only after both dates pass the order check.

Pythonista lens — recoverable errors are values: You may be used to wrapping parsing in try/except. This function instead returns Result<T, E>: either Ok(request) or Err(message). The ? operator means “if this step failed, return that error from this function now; otherwise give me the successful value.” It works because the function itself promises a Result. That makes the error path visible in the function's type, and the UI can turn it into a status message instead of letting bad text reach the network layer.
Pythonista comparison: parse and validate dates

Python commonly signals invalid input by raising an exception, which the caller catches. The built-in tuple[...] type hint shown here requires Python 3.9+. Rust returns a Result value instead, so the success and error paths appear in the function's type.

from datetime import date


def parse_date_range(
    start_text: str,
    end_text: str,
) -> tuple[date, date]:
    start = date.fromisoformat(start_text)
    end = date.fromisoformat(end_text)

    if start > end:
        raise ValueError("Start date must be on or before end date")

    return start, end

Code along: validate coordinates before building a request

Create src/input.rs from the src folder in Zed's file tree. Paste this code and save it with Esc, :w, Enter:

fn parse_coordinate(
    raw: &str,
    label: &str,
    min: f64,
    max: f64,
) -> Result<f64, String> {
    let value = raw
        .trim()
        .parse::<f64>()
        .map_err(|_| format!("{label} must be a number"))?;

    if !(min..=max).contains(&value) {
        return Err(format!("{label} must be between {min} and {max}"));
    }

    Ok(value)
}

pub fn parse_latitude(raw: &str) -> Result<f64, String> {
    parse_coordinate(raw, "Latitude", -90.0, 90.0)
}

pub fn parse_longitude(raw: &str) -> Result<f64, String> {
    parse_coordinate(raw, "Longitude", -180.0, 180.0)
}

Finally, replace src/main.rs with this complete example:

mod app_state;
mod input;
mod models;

use app_state::AppState;
use models::{LocationQuery, WeatherQueryRequest};

fn main() {
    for raw in ["6.52", "west", "120.0"] {
        println!(
            "Latitude {:?} -> {:?}",
            raw,
            input::parse_latitude(raw),
        );
    }

    let latitude = input::parse_latitude("6.52");
    let longitude = input::parse_longitude("3.38");
    let mut state = AppState::new();

    match (latitude, longitude) {
        (Ok(latitude), Ok(longitude)) => {
            state.request = Some(WeatherQueryRequest {
                location: LocationQuery::Coordinates {
                    latitude,
                    longitude,
                },
                start_date: String::from("2026-10-21"),
                end_date: String::from("2026-10-22"),
            });
            state.status = String::from("Coordinates validated");
        }
        (Err(error), _) | (_, Err(error)) => {
            state.status = error;
        }
    }

    println!("Request state:\n{state:#?}");
}

Python connection: In Python, you might call float(raw) and catch a ValueError. Rust returns a Result: either Ok(number) or Err(message). The ? means “if this failed, return the error now.” We check the coordinates before building the request, like a conductor checking a passenger's destination before issuing a ticket.

What changed in the three files, and why?

In Lesson 3, main.rs made up a weather result so we could watch the app state change. In Lesson 4, we step back to an earlier part of the journey: check the location first, then prepare a request. We have not contacted a weather service yet.

1. src/input.rs: check the numbers

A text box gives us text, even when the text looks like a number. The app must check that text before using it as a latitude or longitude. The helper function parse_coordinate does the shared work:

  1. trim() removes spaces around the text.
  2. .parse::<f64>() tries to turn it into a decimal number. f64 is Rust's type for this kind of number.
  3. map_err changes a technical parsing failure into a message a person can understand.
  4. ? means “if parsing failed, stop here and return that error.”
  5. The range check makes sure the number is allowed. The ..= includes both ends of the range.
  6. Ok(value) returns the number after it passes both checks.

The helper is used by two small functions: latitude must be from -90 to 90; longitude must be from -180 to 180. That way, we write the checking steps once and give each kind of coordinate its own correct limits.

&str means the function borrows the text: it can read the text while it works, but it does not take the text away from the caller. The result is either Ok(number) or Err(message). Rust makes us handle both possibilities.

2. src/app_state.rs: save a request only after it passes

We added request: Option<WeatherQueryRequest>. Option means “there may be a value, or there may be no value.” The request starts as None because we have not checked any coordinates yet. After both coordinates pass, it becomes Some(request).

The request and the result are different things. request is what the app plans to ask for. latest_result is where weather data can go after a service answers. Keeping two fields helps us track those two steps separately.

3. src/main.rs: join the steps together

mod input; tells Rust to include the new input.rs file. The use lines let us write model names without their longer paths. The loop tries three examples so we can see one success and two different errors.

Next, match (latitude, longitude) checks both results. If both are Ok, the app builds a WeatherQueryRequest with the Coordinates location and saves it in state.request. If either one is an Err, the app saves the error in state.status. This is the gate that stops bad text from becoming a request.

Reading your output: 6.52 became Ok(6.52). west became an error because it is not a number. 120.0 became an error because it is too large for latitude. The final state shows a request using latitude 6.52 and longitude 3.38. This is a practice example: the app made the request value, but did not send it to a real weather service.
