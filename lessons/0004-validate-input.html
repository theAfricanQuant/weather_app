Before the explanation

parse_date_range returns a Result. What should it return when both dates parse and the start is not after the end?

Validation is a gate with a receipt

The UI starts with strings because that is what text boxes hold. Before networking, build_request checks the date range, matches on the input mode, trims fields, parses coordinate strings into f64, and builds the typed request. The functions return Result so an invalid input has a clear path back to a status message.

fn parse_date_range(&self) -> Result<(NaiveDate, NaiveDate), String> {
    let start = date_utils::parse_date(&self.start_date_input)?;
    let end = date_utils::parse_date(&self.end_date_input)?;
    if start > end {
        return Err("Start date must be on or before End date.".to_owned());
    }
    Ok((start, end))
}

This omits the empty-field checks to keep the pattern visible. The ? operator returns early if parsing fails. The final Ok is reached only after both dates pass the order check.

Pythonista lens — recoverable errors are values: You may be used to wrapping parsing in try/except. This function instead returns Result<T, E>: either Ok(request) or Err(message). The ? operator means “if this step failed, return that error from this function now; otherwise give me the successful value.” It works because the function itself promises a Result. That makes the error path visible in the function's type, and the UI can turn it into a status message instead of letting bad text reach the network layer.
Pythonista comparison: parse and validate dates

Python commonly signals invalid input by raising an exception, which the caller catches. The built-in tuple[...] type hint shown here requires Python 3.9+. Rust returns a Result value instead, so the success and error paths appear in the function's type.

from datetime import date


def parse_date_range(
    start_text: str,
    end_text: str,
) -> tuple[date, date]:
    start = date.fromisoformat(start_text)
    end = date.fromisoformat(end_text)

    if start > end:
        raise ValueError("Start date must be on or before end date")

    return start, end

Code along: validate coordinates before building a request

Create src/input.rs from the src folder in Zed's file tree. Paste this code and save it with Esc, :w, Enter:

fn parse_coordinate(
    raw: &str,
    label: &str,
    min: f64,
    max: f64,
) -> Result<f64, String> {
    let value = raw
        .trim()
        .parse::<f64>()
        .map_err(|_| format!("{label} must be a number"))?;

    if !(min..=max).contains(&value) {
        return Err(format!("{label} must be between {min} and {max}"));
    }

    Ok(value)
}

pub fn parse_latitude(raw: &str) -> Result<f64, String> {
    parse_coordinate(raw, "Latitude", -90.0, 90.0)
}

pub fn parse_longitude(raw: &str) -> Result<f64, String> {
    parse_coordinate(raw, "Longitude", -180.0, 180.0)
}

Finally, replace src/main.rs with this complete example:

mod app_state;
mod input;
mod models;

use app_state::AppState;
use models::{LocationQuery, WeatherQueryRequest};

fn main() {
    for raw in ["6.52", "west", "120.0"] {
        println!(
            "Latitude {:?} -> {:?}",
            raw,
            input::parse_latitude(raw),
        );
    }

    let latitude = input::parse_latitude("6.52");
    let longitude = input::parse_longitude("3.38");
    let mut state = AppState::new();

    match (latitude, longitude) {
        (Ok(latitude), Ok(longitude)) => {
            state.request = Some(WeatherQueryRequest {
                location: LocationQuery::Coordinates {
                    latitude,
                    longitude,
                },
                start_date: String::from("2026-10-21"),
                end_date: String::from("2026-10-22"),
            });
            state.status = String::from("Coordinates validated");
        }
        (Err(error), _) | (_, Err(error)) => {
            state.status = error;
        }
    }

    println!("Request state:\n{state:#?}");
}

Save the files and run cargo run. You should see 6.52 accepted, west rejected as non-numeric, and 120.0 rejected as an invalid latitude. Then the final state contains a coordinate-based request.

Rust and Python side by side: Python might parse with float(raw) and catch ValueError. Here the return type Result<f64, String> makes success or failure part of the function's contract. The ? operator returns early if parsing fails; map_err turns the parser's technical error into a helpful message. We validate before putting coordinates into the request, like checking a danfo passenger's destination before issuing the ticket.
