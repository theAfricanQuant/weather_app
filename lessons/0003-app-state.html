The app struct is its notebook

CyberWeatherApp in app.rs owns the current screen state: input strings, selected mode, loading/status text, the latest result, animation preferences, history, and a receiver for background-worker messages.

struct CyberWeatherApp {
    input_mode: InputMode,
    city_input: String,
    loading: bool,
    status_text: String,
    latest_result: Option<WeatherQueryResult>,
    history_entries: Vec<HistoryEntry>,
    worker_rx: Option<Receiver<WorkerMessage>>,
}

This is a sketch of the real struct. Its constructor sets a ready status, a default city and dates, no result yet, and any saved history it can load. State is like the shopkeeper's ledger: it records the current situation, while later UI code reads it to decide what to show.

Pythonista lens — a struct is a fixed data shape: You can picture CyberWeatherApp as a typed dataclass whose fields have declared types. Unlike a Python instance that can freely gain or change attributes at runtime, this struct has a known set of fields and each field keeps its declared type. Rust also does not call a special __init__ automatically: this project writes a new method to build a complete app value. Notice Option<WeatherQueryResult>: the app starts with None, then holds Some(result) after success. That explicit absence keeps “not loaded yet” distinct from a real result.
Pythonista comparison: app state as a dataclass

WeatherQueryResult stands for the result type defined elsewhere in the app. The | None annotation uses Python 3.10+ syntax and helps readers and type-checking tools; Rust's Option<WeatherQueryResult> also makes callers handle absence in the program.

Code along: store the app's current state

First, update src/models.rs by adding this type at the bottom. In Zed Vim mode, press Esc, then G to go to the last line, then o to open a new line below and paste the block with Edit → Paste. Save with Esc, :w, Enter.

#[derive(Debug)]
pub struct WeatherQueryResult {
    pub location: String,
    pub temperature_c: Option<f64>,
}

Create src/app_state.rs from the src folder in Zed's file tree, and put this code in it:

use crate::models::WeatherQueryResult;

#[derive(Debug)]
pub struct AppState {
    pub input_location: String,
    pub loading: bool,
    pub latest_result: Option<WeatherQueryResult>,
    pub status: String,
}

impl AppState {
    pub fn new() -> Self {
        Self {
            input_location: String::from("Lagos"),
            loading: false,
            latest_result: None,
            status: String::from("Ready"),
        }
    }
}

Now replace all of src/main.rs with this, using Esc, gg, dG, i, Edit → Paste, then Esc, :w, Enter:

mod app_state;
mod models;

use app_state::AppState;
use models::WeatherQueryResult;

fn main() {
    let mut state = AppState::new();
    println!("Starting state:\n{state:#?}");

    state.latest_result = Some(WeatherQueryResult {
        location: String::from("Lagos, Nigeria"),
        temperature_c: Some(31.0),
    });
    state.status = String::from("Weather loaded");

    println!("Updated state:\n{state:#?}");
}

Save all three files and run cargo run. First, the output shows latest_result: None; after our update it shows Some(...). We use let mut because this code changes the state after creating it. In Python you can usually reassign an object attribute directly; Rust asks us to mark a binding mutable before we change through it.

Why this structure? The app state is the shopkeeper's current ledger: loading status, input, message, and latest result stay together. Option<WeatherQueryResult> distinguishes “no result yet” from a real measurement such as Some(0.0). It is safer than treating zero as a missing-value marker.
