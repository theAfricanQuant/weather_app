The app struct is its notebook

CyberWeatherApp in app.rs owns the current screen state: input strings, selected mode, loading/status text, the latest result, animation preferences, history, and a receiver for background-worker messages.

struct CyberWeatherApp {
    input_mode: InputMode,
    city_input: String,
    loading: bool,
    status_text: String,
    latest_result: Option<WeatherQueryResult>,
    history_entries: Vec<HistoryEntry>,
    worker_rx: Option<Receiver<WorkerMessage>>,
}

This is a sketch of the real struct. Its constructor sets a ready status, a default city and dates, no result yet, and any saved history it can load. State is like the shopkeeper's ledger: it records the current situation, while later UI code reads it to decide what to show.

Pythonista lens — a struct is a fixed data shape: You can picture CyberWeatherApp as a typed dataclass whose fields have declared types. Unlike a Python instance that can freely gain or change attributes at runtime, this struct has a known set of fields and each field keeps its declared type. Rust also does not call a special __init__ automatically: this project writes a new method to build a complete app value. Notice Option<WeatherQueryResult>: the app starts with None, then holds Some(result) after success. That explicit absence keeps “not loaded yet” distinct from a real result.
